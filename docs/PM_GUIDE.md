# 프로젝트 관리 가이드 — 양식 설계 근거와 운영 방법

이 도구의 시트 양식은 아래 레퍼런스에서 공통적으로 권하는 방식을 따릅니다.
목표는 "**적게 입력하고, 나머지는 수식이 계산하고, 문제는 색으로 드러나게**"입니다.

## 1. 레퍼런스에서 얻은 원칙

| 원칙 | 내용 | 이 양식에 반영한 방식 |
|---|---|---|
| 입력 칸은 최소로 | 컬럼은 5~8개로 시작합니다. 매주 갱신할 칸은 상태·진척률·블로커 정도로 줄입니다. | 사람이 고치는 칸은 왼쪽 A~K에만 두었습니다. 매주 고칠 칸은 **상태·진척률**뿐입니다. |
| 입력값 통일 | 상태·우선순위는 드롭다운으로만 입력하게 해서 표기가 제각각이 되지 않게 합니다. | 상태·우선순위·날짜·진척률에 입력 검증을 걸었습니다. |
| 계산은 수식으로 | 지연 여부, 집계, 상태 롤업을 손으로 쓰지 않습니다. | 계획진척률, 일정차이, 남은일수, 일정변경, 기간, 대시보드 전체를 수식으로 계산합니다. |
| 위험은 색으로 | 지연·위험·차단 작업이 눈에 띄도록 조건부 서식을 겁니다. | 지연(빨강), 차단(주황), 완료(초록)로 칠합니다. 일정차이 -5%·-15%와 일정변경 +일수에도 색을 넣었습니다. |
| WBS(작업 분해) | 단계나 산출물 단위로 묶어야 필터링과 롤업이 됩니다. | **단계** 열을 추가했습니다. `0.사전준비`, `1.기반`처럼 번호를 붙이면 정렬하기 쉽습니다. |
| 기준선(Baseline)과 실적 | 처음 승인한 일정을 덮어쓰지 않고, 바뀐 일정과의 차이를 봅니다. | **기준종료일**은 처음 정한 종료일로 자동 고정됩니다. **일정변경(일)** = 현재 종료일 − 기준종료일입니다. |
| 선행 관계(Dependency) | 선행작업 ID를 기록하고, 선행이 끝나지 않았으면 블로커로 표시합니다. | **선행작업** 열에 `T-001, T-003`처럼 씁니다. 선행 중 미완료가 있으면 그 칸이 주황색이 됩니다. |
| 계획 대비 실적(SV) | 일정 차이 = 실제 진척률 − 계획 진척률입니다. 음수면 늦은 것입니다. | **계획진척률**은 오늘 날짜가 작업 기간의 몇 %에 와 있는지로 계산합니다. **일정차이** = 진척률 − 계획진척률입니다. |
| RAG 건강도 | 정상/주의/위험의 기준을 **미리 정해 두고** 바꾸지 않습니다. 예: 5% 이내 정상, 5~15% 주의, 15% 초과 위험. | 대시보드 **건강도**가 아래 기준으로 자동 판정됩니다. |
| RAID 로그 | 리스크·가정·이슈·의존성을 한 곳에 모읍니다. 항목마다 고정 ID, 담당자, 날짜를 둡니다. 리스크가 실제로 터지면 이슈로 옮깁니다. | **RAID** 시트를 만들었습니다. 유형은 리스크·가정·이슈·의존성·결정이고, R-001부터 ID가 자동으로 붙습니다. |
| 사본은 하나만 | 첨부파일로 주고받지 말고, 링크 하나로 함께 봅니다. | 구글 시트 하나를 공유해서 씁니다. |
| 정기 점검 | 주 1회 짧게 일정·우선순위·담당을 점검합니다. | 아래 "운영 루틴"을 참고하세요. |

## 2. 시트 구성

### 대시보드 (프로젝트당 1행, 모두 자동)
| 열 | 의미 |
|---|---|
| 작업수 / 완료 | 전체 작업 수와 완료된 작업 수 |
| 진척률 | 전체 작업 진척률의 평균 |
| 기간경과 | 프로젝트 기간 중 지난 비율. 진척률과 나란히 보면 대략적인 페이스를 알 수 있습니다. |
| 일정차이 | 날짜가 있는 작업들의 (진척률 − 계획진척률) 평균. 날짜가 없는 작업은 빠집니다. |
| 지연 | 종료일이 지났는데 완료되지 않은 작업 수 |
| 차단 | 상태가 `차단`인 작업 수 |
| 열린 RAID | 해결·종료되지 않은 RAID 항목 수 |
| 다음 마감 | 완료되지 않은 작업 중 가장 빠른, 오늘 이후의 종료일 |
| 건강도 | 아래 기준 |

**건강도 기준** (`gtrack/layout.py`의 `VARIANCE_WARN`, `VARIANCE_RISK`)
- 🔴 **위험**: 일정차이 −15% 이하, 또는 지연 3건 이상
- 🟡 **주의**: 일정차이 −5% 미만, 지연·차단 1건 이상, 또는 영향도 `높음`인 열린 RAID가 있음
- 🟢 **정상**: 위 조건에 해당하지 않음
- 작업이 없으면 `대기`, 전부 완료면 `완료`

### 프로젝트 시트 (프로젝트마다 1개)
| 구분 | 열 |
|---|---|
| **입력** (파란 헤더) | ID · 단계 · 작업명 · 담당자 · 우선순위 · 상태 · 진척률 · 시작일 · 종료일 · 선행작업 · 비고 |
| **자동** (회색 헤더) | 계획진척률 · 일정차이 · 남은일수 · 기준종료일 · 일정변경(일) · 완료일 · 기간(일) |
| **간트** | 주 단위 막대입니다. 진행은 파랑, 차단은 주황, 완료는 초록이고, 이번 주 열은 노랑입니다. |

- 상태: `대기` → `진행중` → `완료`. 막히면 `차단`, 일부러 멈추면 `보류`
  - 진척률을 100으로 하면 자동으로 `완료`가 되고 **완료일**이 기록됩니다.
- 기준종료일: 종료일을 처음 정할 때 자동으로 기록됩니다. 의도적으로 기준을 다시 잡을 때만 손으로 고칩니다(재기준선).

### RAID 시트 (모든 프로젝트 공용)
ID · 프로젝트 · 유형 · 내용 · 영향도 · 담당자 · 대응방안 · 상태 · 등록일 · 기한 · 관련작업

| 유형 | 언제 쓰나 |
|---|---|
| 리스크 | 아직 일어나지 않았지만 일어날 수 있는 문제 |
| 가정 | 확인되지 않았지만 계획의 전제로 삼은 것 |
| 이슈 | 지금 일어나서 해결이 필요한 문제 |
| 의존성 | 다른 팀이나 외부에서 받아야 하는 것, 또는 넘겨줘야 하는 것 |
| 결정 | 나중에 "왜 이렇게 했지?"에 답할 수 있게 남기는 결정 기록 |

- 상태는 `열림` → `대응중` → `해결` / `종료`로 바뀝니다.
- 열린 항목 중 영향도 `높음`은 빨간색, `이슈`는 주황색으로 표시됩니다.
- 리스크가 실제로 일어나면 이슈를 새로 등록하고, 원래 리스크는 `종료`로 바꾼 뒤 대응방안에 새 이슈 ID를 적습니다.

## 3. 운영 루틴

| 주기 | 할 일 | 명령 |
|---|---|---|
| 작업이 움직일 때 | 진척률이나 상태 갱신 | `task update <프로젝트> T-xxx --progress 60` |
| 주 1회 (15분) | ① 대시보드 건강도 확인 ② `--open` 목록으로 지연·차단 점검 ③ 날짜가 빈 작업에 일정 넣기 ④ RAID 열린 항목 점검 | `project list` · `task list <프로젝트> --open` · `raid list --open` |
| 새 리스크나 이슈가 생길 때 | RAID에 등록 | `raid add <프로젝트> 리스크 "내용" --impact 높음` |
| 일정이 바뀔 때 | 종료일만 바꿉니다. 기준종료일은 그대로 두면 일정변경(일)에 자동으로 기록됩니다. | `task update <프로젝트> T-xxx --end 2026-11-30` |
| 마일스톤 | 단계가 끝날 때 남은 작업의 일정을 다시 잡습니다. | |

**좋은 작업 단위**
- 1~10일 안에 끝나는 크기로 나눕니다. 더 크면 쪼갭니다.
- "완료"가 무엇인지 분명해야 합니다. 예: "검색 결과 페이지 이관 + E2E 통과"
- 시작일과 종료일을 넣어야 계획진척률·일정차이·간트에 나타납니다. 날짜가 없는 작업은 일정 관리 대상에서 빠집니다.
