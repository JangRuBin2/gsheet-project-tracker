# ops-request — 운영 개선 요청서 시트 기록

대상: https://docs.google.com/spreadsheets/d/1V-Ducwkd00AyBml_UxEWL6NR32fcZ70bdRloicsz3g4/edit (gid=1881570671, 「요청 목록」 탭)

**gtrack 양식이 아니다.** `gtrack --id …` 로 다루지 말고 아래 스크립트를 쓴다.

```
python "$HOME/gsheet-project-tracker/gsheet-project-tracker/skill/ops-request/scripts/ops_request.py" <명령>
```
| 명령 | 하는 일 |
|---|---|
| `show` | 채워진 행 요약 (No · 요청일 · 요청자 · 서비스 · 메뉴 · 상태 · 반영일 · 작성 점검) |
| `add <row.json>` | 첫 빈 행에 요청 1건 추가. `shots` 가 있으면 드라이브에 올리고 M 칸에 링크 |
| `reply <No> <reply.json>` | 개발팀 칸(O~S) 중 준 키만 갱신 |
| `shots <No> <이미지...> [--force]` | 캡처를 `운영 개선 요청 스크린샷/No-<No>` 폴더에 올리고 M 칸에 `=HYPERLINK(폴더, "캡처 n장 …")`. 같은 이름 파일은 건너뜀 |

- JSON 은 scratchpad 에 UTF-8 로 만든다. 저장소에 두지 않는다.
- 첫 실행 · 7일 뒤 토큰 만료 시 브라우저 로그인이 뜬다. `$env:PYTHONUNBUFFERED=1` 로 백그라운드 실행하고 사용자에게 로그인을 부탁한다.
- 토큰은 gtrack 설치 폴더의 `token_ops.json`(spreadsheets + drive.file). gtrack 의 `token.json` 과 따로다. 내용을 읽거나 출력하지 않는다.

## 시트 양식

| 열 | 내용 | 쓰는 쪽 |
|---|---|---|
| A | No — `=IF(B="","",ROW()-5)` 수식 | **쓰지 않음** |
| B~M | 요청일 · 요청자 · 서비스 · 메뉴 경로 · 화면 URL · 사용 환경 · 유형 · 긴급도 · 현상 / 문제점 · 재현 방법 / 대상 데이터 · 기대 결과 · 스크린샷 | ① 운영팀 (개발팀 자체 개선이면 우리가 씀) |
| N | 작성 점검 — 필수 칸이 비면 「누락: …」 수식 | **쓰지 않음** |
| O~S | 담당자 · 상태 · 회신 / 조치 계획 · 완료 예정일 · 운영 반영일 | ② 개발팀 |
| T~U | 확인 결과 · 추가 요청 내용 | ③ 운영팀 — **쓰지 않음** |

- 5행은 작성 예시, 데이터는 6행(No 1)부터. No = 행 − 5.
- 드롭다운 값은 「목록」 탭에서 읽어 검사한다(스크립트가 막는다). 2026-11 기준:
  - 서비스: 협력사 관리자(SRM) · 통합 관리자(IPOS) · 쇼핑몰 (사용자) · 판매자 관리자(셀러) · 기타 · 미래엔 · 미래엔 관리자
  - 사용 환경: PC · 모바일 웹 · 앱 · PC + 모바일
  - 유형: 오류(버그) · 화면·UI 개선 · 기능 추가·변경 · 문구 수정 · 데이터 확인 · 기타
  - 긴급도: 긴급(업무 중단) · 높음 · 보통 · 낮음
  - 상태: 접수 · 검토 중 · 진행 중 · 개발 완료(확인 요청) · 운영 반영 · 보류 · 반려
- 서비스는 하나만 고를 수 있다. 여러 화면에 적용되면 대표 하나를 고르고 나머지는 메뉴 경로 · 회신에 적는다.

## JSON 키

`add` (필수 ★):
```json
{
  "요청일": "2026-11-17", "요청자": "개발팀", "서비스": "협력사 관리자(SRM)",
  "메뉴 경로": "상품 관리 > 재고수량 관리", "화면 URL": "", "사용 환경": "PC",
  "유형": "기능 추가·변경", "긴급도": "보통",
  "현상": "…", "재현 방법": "1) …\n2) …", "기대 결과": "…",
  "shots": ["C:/workspace/bx_api/docs/plans/<문서>/before-1.jpg", "…/after-1.jpg"],
  "담당자": "", "상태": "운영 반영", "회신": "2026-11-17 운영 반영: …",
  "완료 예정일": "2026-11-17", "운영 반영일": "2026-11-17"
}
```
★ = 요청일 · 요청자 · 서비스 · 메뉴 경로 · 사용 환경 · 유형 · 긴급도 · 현상 · 기대 결과. `reply` 는 `담당자 · 상태 · 회신 · 완료 예정일 · 운영 반영일` 중 바꿀 키만.

## 작업 절차

1. **자료 읽기.** 작업 설명 PDF(Read 로 읽음)나 `C:/workspace/<repo>/docs/plans/<날짜>-<제목>.md` 를 읽는다. PDF 마지막 줄의 「개발자용 상세: docs/plans/…」 로 원본 문서를 찾는다.
2. **기존 행 확인.** `show` 로 같은 작업을 이미 받은 요청 행이 있는지 본다.
   - 운영팀이 올린 요청에 대한 조치면 **새 행을 만들지 않고** `reply` 로 그 행의 회신을 단다.
   - 개발팀 자체 개선이거나 사용자가 새 행을 원하면 `add`.
3. **운영 반영 여부는 git 으로 확인한다.** 관련 커밋이 `origin/release`(없으면 `origin/master`/`main`)에 들어 있으면 `운영 반영` + 운영 반영일. develop 에만 있으면 `개발 완료(확인 요청)`. 추측하지 않는다.
4. **스크린샷.** `docs/plans/<문서명>/` 폴더의 `before-*` · `after-*` 이미지를 순서대로 넣는다. 없으면 사용자에게 캡처 위치를 묻는다. 고객 개인정보(이름 · 연락처 · 주소)가 보이는 캡처는 올리지 말고 알린다.
5. **문장.** 비개발자(운영팀)가 읽는다. 개발 용어 · 파일명 · API 경로를 쓰지 않는다. PDF 의 「지금 / 바뀐 뒤 / 주의」 를 현상 · 기대 결과 · 회신으로 옮긴다. 회신은 `YYYY-MM-DD 운영 반영: …` 형식(기존 행과 같은 말투). 자료에 없는 내용은 지어내지 않는다.
6. 끝나면 `show` 로 확인하고, 들어간 행(No · 상태 · 반영일)과 **임의로 정한 값**(요청자 · 서비스 대표값 · 긴급도 등)을 보고한다.

## 정해진 값

- 개발팀 자체 개선 행의 요청자: `개발팀`. 담당자는 사용자가 말하지 않으면 비워 둔다.
- 요청일: 작업 문서(PDF) 날짜. 운영 반영일: release 머지 날짜.
- T · U 열(운영팀 확인)과 A · N 열(수식)은 절대 쓰지 않는다. 이미 값이 있는 칸을 덮어쓸 때는 먼저 사용자에게 묻는다.

## 드라이브 폴더 공유

- 스크린샷 폴더는 로그인한 계정의 내 드라이브 `운영 개선 요청 스크린샷/` 아래에 만들어진다. 스크립트는 **공유 설정을 바꾸지 않는다**.
- 운영팀이 링크를 열려면 상위 폴더 `운영 개선 요청 스크린샷` 을 운영팀과 한 번 공유해야 한다(하위 폴더는 상속). 처음 만들어졌을 때 사용자에게 안내한다.
