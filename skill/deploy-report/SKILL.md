# deploy-report — 운영 적용 내용 보고

상사에게 보낼 "오늘 운영에 적용할 내용"을 레포별로 아주 짧게 정리한다.

## 출력 형식 (이 형식 그대로 — 2026-11-05 사용자가 직접 고쳐 준 형식)

```
[미래엔]
- 아이디어 제안 분류에 원클릭 패키지 제안 · 상품 등록 제안 추가

[미래엔 관리자, ipos, company, 협력사 관리자, 셀러]
- 주문 목록 기본 조회 기간 조정 > 전체에서 1개월로, 최대 1년까지 범위 제한
- 주문승인 목록 > 페이지네이션 적용
- 주문승인 처리 오류 개선 > 마지막 페이지에서 작업후 빈페이지 노출
```

- **여러 서비스에 같은 작업이 들어갔으면 서비스 이름을 쉼표로 묶어 한 블록에 한 번만 쓴다.**
  서비스마다 같은 줄을 되풀이하지 않는다. 한 서비스에만 있는 작업만 그 서비스 블록에 따로 쓴다.
- 한 줄은 `무엇 > 어떻게` 형식을 쓸 수 있다. `>` 뒤에 바뀐 내용을 짧게 붙인다(전 → 후, 적용 범위).
- 「오늘 작업내용」을 물으면 운영 적용분만이 아니라 **그날 한 작업 전부**를 쓴다. 운영 승인 전
  (develop · 작업 브랜치만) 작업과 커밋 없는 조사 · 데이터 확인은 별도 블록(`[개발 중]`, `[기타]`)으로 뒤에 둔다.
  「운영 적용 내용」「배포 내용」을 물을 때만 승인 · 운영 브랜치 커밋으로 거른다.
- 대괄호에는 레포 이름이 아니라 **서비스 이름**을 쓴다. 레포 → 서비스 이름:

| 레포 | 대괄호 이름 |
|---|---|
| bx_miraen | 미래엔 |
| bx_miraen_admin | 미래엔 관리자 |
| bx_company | company |
| bx_srm_c | 협력사 관리자 |
| bx_ipos | ipos |
| bx_seller | 셀러 |
| bx-store | 굿즈베이커리 (Next.js) |

- 서비스는 커밋 메시지가 아니라 **저장소**로 정한다. bx_srm_c 의 `*-miraen` 화면은 미래엔(엠티처몰) 협력사몰의 협력사용 화면이라, 메시지에 「(미래엔)」이 있어도 `[미래엔 관리자]`가 아니라 bx_srm_c 의 이름 아래에 쓴다.
- 백엔드(bx_api) 수정은 따로 묶지 않고 **그 기능을 쓰는 서비스** 아래에 넣는다. 화면 수정과 같은 기능이면 한 줄로 합친다(예: API 상품코드 추가 + 관리자 상품코드 컬럼 → `[미래엔 관리자]` 한 줄). 여러 서비스가 같이 쓰는 서버 수정만 `[공통 API]`에 쓴다.
- 표에 없는 레포는 README·index.html 제목으로 서비스 이름을 짐작하고, 짐작한 이름은 보고 블록 밖에서 맞는지 묻는다.
- 서비스 사이에 빈 줄 하나. 순서는 항목이 많은 서비스 먼저, `[공통 API]`는 맨 뒤.
- 한 줄은 "무엇을 + 추가/수정/개선/차단/적용" 으로 끝나는 명사형. 원인·방법·커밋 해시·파일명·괄호 설명은 쓰지 않는다.
  - 좋음: `관리자 상품 목록 조회에 상품코드 추가`
  - 나쁨: `관리자 굿즈 목록: LIMIT 전에 2.3만 행 계산하던 감싸개 제거 (admin, store)`
- 한 커밋에 기능이 여러 개면 줄을 나눈다. 같은 기능을 여러 커밋으로 고쳤으면 한 줄로 합친다.
- 같은 기능이 같은 서비스 안에서 여러 레포(API + 화면)에 걸치면 한 줄로 합친다.
- 보고 블록 안에는 목록만 쓴다. 인사말·요약·주의사항은 넣지 않는다.

## 수집 방법

1. 커밋 모으기 (날짜는 기본 오늘, 사용자가 말하면 그 날):

```bash
D=$(date +%F)
cd /
for r in c/workspace/*/; do r=${r%/}
  [ -d "$r/.git" ] || continue          # worktree(.git 이 파일)는 원본 레포와 같으니 건너뜀
  git -C "$r" fetch -q 2>/dev/null
  out=$(git -C "$r" log --all --since="$D 00:00" --author=rubinjang --no-merges \
        --date=format:%H:%M --format='%ad %h %s')
  [ -n "$out" ] && echo "=== ${r##*/}" && echo "$out"
done
```

2. 운영에 들어갈 커밋만 남긴다. 커밋마다 승인 브랜치나 운영 브랜치에 들어갔는지 확인한다.

```bash
git -C <레포> branch -r --contains <해시> | grep -E 'origin/(release|master|main)$'
```
- **2026-11-03 부터 운영 배포는 `release` 브랜치에서만 한다** (`feat/* → develop → (승인) master/main → release → 운영`).
  승인 브랜치는 레포마다 다르다. bx_miraen_admin · bx_seller 는 `main`, 나머지는 `master`. `git -C <레포> symbolic-ref refs/remotes/origin/HEAD` 로 확인.
- 넣는 커밋:
  - `master`/`main` 에 있고 `release` 에 없는 커밋: 승인을 받았고 이번 배포에 나갈 것
  - `release` 에도 있는 커밋: 이미 운영에 나갔다. 오늘 날짜 커밋이면 넣는다
- `master`/`main` 에도 `release` 에도 없는 커밋(develop 만, 작업 브랜치만)은 뺀다. 사용자가 "개발 배포 포함"이라고 하면 develop 도 넣는다.

3. 뺄 것
- `[docs]` 커밋, 병합 커밋, stash 커밋(`index on …`, `On …:` 로 시작)
- 같은 내용이 체리픽·배포용 브랜치로 여러 번 찍힌 커밋은 하나로 본다.
- 개발 서버·로컬 전용 수정(예: 개발 SSO, 개발 도메인 설정)은 운영 브랜치에 들어갔어도 사용자 화면에 변화가 없으면 뺀다. 애매하면 넣고 아래 주의사항에서 물어본다.

## 보고 블록 밖에 덧붙일 것 (있을 때만, 짧게)

- 배포 순서나 선행 작업이 필요한 항목(예: 운영 DB 데이터 정리 후 배포해야 하는 서버 수정). "이 줄은 ~ 전에는 빼고 보고하세요"처럼 한두 줄.
- 승인 · 운영 브랜치에 병합됐는지 확인 못 한 항목.
- `master`/`main` 에는 있지만 아직 `release` 에 없는 항목이 섞였으면 「아직 운영 배포 전」이라고 한 줄로 알린다.

## 하지 말 것

- 보고 문구를 상사나 다른 사람에게 직접 보내지 않는다. 사용자에게 텍스트로만 준다.
- 커밋이 없는 작업(운영 DB 수동 정리 등)은 사용자가 넣으라고 할 때만 넣는다.
